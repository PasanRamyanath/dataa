1. Executive Summary
This plan specifies an ensemble machine-learning system that forecasts short-horizon Binance USDT-margined
futures (BTCUSDT primary; extensible to other pairs) price movement, fuses in a free-tier real-time news/social
sentiment signal, and evaluates itself through a realistic paper-trading simulation — with every stage, from raw
data acquisition through live inference and signal streaming, running inside Kaggle notebooks on dual NVIDIA
T4 GPUs. It is the direct successor to the ~15 draft plans already in Project-IMPJR, reconciling their
contradictions into one coherent, buildable specification, and it is sized against the exact Kaggle resource figures
you measured (~30GB RAM, ~30GB VRAM, ~57GB temp storage, 20GB persistent output storage).
What this system does

Acquires and feature-engineers Binance futures + spot microstructure data (klines, trades, order book,
funding, open interest, premium index) entirely inside a Kaggle CPU-only notebook, publishing unified
Parquet to a Hugging Face dataset that training/inference notebooks stream from.

Trains a heterogeneous 9-member ensemble (a fine-tuned domain foundation model, four
transformer/SSM sequence architectures, a gradient-boosted-tree family, a regime classifier, and a
sentiment-fusion branch) that each specialize in a different horizon, feature subset, or signal type.

Combines all members through a regime-gated stacking meta-learner and a meta-labeling filter that
decides not just direction but whether a signal is confident enough to act on at all.

Runs per-second-cadence inference across both T4s whenever a Kaggle session is active, relaunching
the next session within minutes via an automated, ToS-compliant relay — minimizing every avoidable gap
— and fills spare GPU/CPU capacity every tick with productive work rather than letting it idle (§13).

Streams every signal out live via a stable Cloudflare Tunnel hostname and outbound webhooks, sourced
entirely from the Kaggle session (§14), while keeping a hard boundary: paper-trading only, no live order
ever reaches Binance.

Retrains and is re-validated on a recurring schedule against multiple independent market regimes, with
mandatory naive-baseline comparison, because that is the single biggest reason comparable public
projects fail (§10).

reconfirmed platform ceilings — the 12h limit has been standing since a January 2022 update, not something

quantification — rather than running a mostly-idle forward pass (§13). The honest result is the closest a single
Kaggle account can get to continuous, with every remaining gap logged and reported, never hidden (§12.4).

6. Labeling, Targets & Loss Design
This is the area where your prior drafts diverged most (§2) — raw price forecast vs. categorical signal vs.
Sharpe-maximizing meta-output. This plan unifies it around a two-stage labeling scheme that is current
best-practice for exactly this kind of high-frequency, noisy financial target.
6.1 Primary label: triple-barrier
For each entry point in the training set, define three barriers on the forward price path: an upper (profit-take)
barrier, a lower (stop-loss) barrier, and a time barrier (max holding period). The label is which barrier is touched
first. Barrier widths are set as a multiple of a rolling realized-volatility estimate (not a fixed price distance), so
labels stay meaningful across both quiet and volatile regimes.

6.3 Secondary label: meta-labeling
On top of the primary triple-barrier label, train a secondary binary model (part of the meta-learner stage, §8)
whose target is "was the primary ensemble's directional call correct," conditioned on the primary call itself. This is
the standard mechanism for converting a noisy directional signal into a precision-focused act/AVOID decision,
consistent with an expected 40-60% AVOID rate on the primary signal.
6.4 Loss functions

Sequence models: a blended loss of directional cross-entropy + quantile loss (for TFT's native quantile
heads) + a magnitude-aware term (GMADL-style: reward sign-correctness scaled by move magnitude)
rather than plain MSE.

GBM family: standard binary/multiclass objective on the triple-barrier label, with sample weighting inverse
to label overlap.

Meta-learner: binary cross-entropy on the meta-label, calibrated afterward with conformal prediction so
the emitted confidence has an actual empirical coverage property.

8. Ensemble Fusion, Regime Gating & Meta-Labeling
8.1 Two-stage fusion
Stage A — Stacking: each of the 9 members' outputs (direction probability + confidence, or quantile forecast
collapsed to a direction+confidence) become input features to a meta-learner (a shallow LightGBM or
ridge/logistic model — kept simple deliberately, since a complex meta-learner on top of an already-complex
ensemble is a classic overfitting trap). Stage B — Regime gating: the HMM's regime-probability vector (member
#8) multiplies each base member's contribution weight before stacking, so e.g. the SSM challenger's weight can
be automatically suppressed in regimes where it's shown to underperform, without hand-tuning.
8.2 Meta-labeling filter
The stacked output feeds a second, separate binary model (§6.3) that decides act/AVOID, producing the final
LONG-leaning / SHORT-leaning / AVOID signal with a calibrated confidence score.
8.3 Calibration
Apply conformal prediction on top of the final confidence score, calibrated on a held-out slice never used in any
training or meta-learner fitting step, so the reported confidence has an actual empirical coverage guarantee
rather than being an arbitrary model-internal number — in Revision 2 this is further sharpened using the free
uncertainty signals from §13.3.

9. News & Sentiment Pipeline (Free-Tier Only)
Being direct about the premise: current research does not support the idea that scraping headlines every 10
seconds gives Bitcoin-specific alpha on its own. Liquid BTC markets have been shown to react to major news
within seconds — a 10-second-lag pipeline is very plausibly reacting to a move the market has already made.
Where a lag-tolerant text signal can plausibly help is (a) sustained sentiment drift/aggregated social-volume
trend over minutes-to-hours rather than single-headline reaction, and (b) less-covered, less-arbitraged news.
This pipeline is designed around that finding.
9.1 Sources (free tier)

RSS headline feeds from CoinDesk, CoinTelegraph, The Block, and Decrypt — headlines/summaries are
explicitly intended for redistribution via RSS, avoiding the ToS risk of scraping full article bodies. Poll
every 10 seconds with conditional GET (ETag/If-Modified-Since) so repeated polls finding nothing new
cost almost nothing.

GDELT's global news event/tone stream (free, 15-minute update cadence) as a slower macro-sentiment
drift feature.

A free-tier on-chain "whale alert"-style large-transfer feed — public blockchain data, not scraped text, so it
carries essentially no ToS/legal exposure and is genuinely near-real-time.

Explicitly excluded: CryptoPanic's API (its free developer tier ended in early 2026), and any X/Twitter
access (the current paid API is $0.005-0.01/read with hard volume caps, and unauthorized scraping is an
active area of X litigation).
9.2 Scoring model
A quantized (int8) distilled FinBERT-class sentiment classifier runs continuously on whichever GPU has spare
headroom (well under 500MB at fp16/int8). It scores each new headline for polarity, magnitude, and a
confidence score; a mention-velocity counter tracks story volume per rolling window. No general-purpose LLM is
used for per-headline real-time scoring at 1Hz — an unoptimized 7B model on a T4 runs at only ~4
tokens/second, and that compute is needed by the price-prediction members. Instead, a small quantized LLM
stays loaded and warm in VRAM continuously and processes batches of recent headlines only when triggered
by a distinct new story (event-triggered, not per-tick) — §13.4 details how spare capacity makes this allocation
somewhat more generous than a bare-minimum build without pretending it can run at 1Hz.
9.3 Fusion into the ensemble
Sentiment enters two ways, matching current published methodology (SentiStack, 2025): (1) as an engineered
feature vector concatenated into the iTransformer and GBM members' inputs, and (2) as its own branch whose
output feeds the stacking meta-learner in §8 directly, so the meta-learner learns how much weight sentiment
deserves per regime rather than that weight being fixed by hand.

10. Validation & Anti-Overfitting Protocol
This section exists because of a specific, sobering 2026 finding: a review of 23 peer-reviewed BTC
forecasting papers found that under rigorous purged walk-forward validation with realistic fees, roughly 92% of
published models lost their apparent edge — none consistently beat a naive persistence baseline at 1-6
month horizons. The failure modes were consistent: non-stationarity across market eras, backtest overfitting,
subtle look-ahead leakage, and mistaking autocorrelation-driven low error on price levels for genuine
predictive skill on price changes. Every safeguard below targets one of these specific failure modes.
10.1 Mandatory validation structure

Purged, embargoed walk-forward cross-validation — never a plain shuffled split.

Multi-regime out-of-sample testing — the 2021-2023 regime-diversity holdout (§4.4) is evaluated as a
genuinely separate test, reported separately from the 2024-2026 in-regime results.

Naive baselines on every report, no exceptions — persistence, a random walk with drift, and
buy-and-hold, computed alongside every model/ensemble result. Any reported edge under ~1% relative
to the naive baseline is treated as noise.

Fees and slippage included in every backtest and paper-trade evaluation, applied identically to the
model and the naive baselines.

12.1 Per-session inference loop design

t+0.0s — pull latest market data increment (REST/WebSocket) and any new news items since last poll
(§9); update rolling feature windows incrementally rather than recomputing from scratch.

t+0.1-0.6s — all 9 ensemble members' forward pass in parallel: GPU 0's members and GPU 1's members

and Python-side orchestration typically are.


models), run on CPU while GPUs are freed for the next tick's data prep.

t+0.8-1.0s — write prediction record + (if the meta-labeling filter says "act") a simulated paper-trade
update; push to the streaming layer (§14).

Remaining spare cycles each tick — filled productively, not idled: see §13.

Loop latency is logged continuously; if it can't sustain 1Hz, it degrades to the fastest cadence it can
sustain and reports that honestly rather than silently dropping ticks.
12.2 Paper-trading engine
Reuses the position-sizing and risk-control logic from the Grok4/Plan-Claude lineage, with no path to a live order
anywhere in the code (no exchange API key with trade permission is ever loaded in the inference notebook):

Position sizing: confidence-scaled sizing (base size × confidence² × a regime multiplier from the HMM
gate), simulated against a fixed paper-trading capital base.

Circuit breakers: simulated daily-loss and weekly-loss thresholds that halt/reduce simulated sizing.

Every simulated trade logs entry/exit price, size, realized P&L, triggering signal, and
confidence/calibration score.
12.3 Storage discipline within confirmed limits
Prediction/trade logs are flushed to Parquet every few seconds (not every tick) and rotated off /kaggle/working to
the versioned Kaggle Dataset before approaching the 20GB output limit; any mid-session scratch (re-fetched
shards, temporary buffers) stays within the ~57GB temp budget and is not expected to survive past session end.
12.4 Honest gap reporting
Because inference only runs during active Kaggle sessions, the prediction/trade log explicitly records session
start/end timestamps. Any analysis of paper-trading performance reports coverage ("active X% of the evaluation
period" — ~12-13% baseline or ~15-17% with TPU-offload, §11.3) alongside the performance numbers, so a
good-looking Sharpe ratio is never presented without the uptime context needed to interpret it honestly.

13. Resource Maximization: Using Every Idle Cycle Productively
A modest 9-member ensemble at 1Hz does not saturate two T4s. Rather than let that headroom sit idle, this
section specifies three concrete, research-backed uses for it, per your instruction to consume available
resources every second rather than run a mostly-idle loop. Each carries an honesty note about how proven it
actually is — none of this is required for the core system to work.
13.1 Drift-gated online adaptation
Between full retraining cycles (§11), lightweight continual updates keep members adapted to very recent data
using otherwise-idle cycles:

GBM family: LightGBM's refit (cheap leaf-value updates on new data, structure fixed) for fast, low-risk
adaptation; continued boosting (init_model=...) only when a drift detector fires, since continued boosting
alone can drift-chase.

Deep sequence members: a small adapter/“fast-weights” layer fine-tuned on the last few minutes of
data, following the “Proactive Model Adaptation” (Proceed, KDD 2025) pattern: estimate drift magnitude
between the recent training distribution and the current data first, and only adapt when that estimate
crosses a threshold — adapting on every tick regardless of actual drift is the drift-chasing failure mode
documented in 2024/25 incremental-learning benchmarks (a Numerai-style incremental framework still
showed large drawdowns through genuine regime breaks even with continuous adaptation).

Anti-forgetting safeguard: keep a small replay buffer of older, diverse examples alongside recent-data
updates, and treat the last full retrain as a periodic “anchor” online adaptation is never allowed to drift
arbitrarily far from.
Honesty check: production-proven track records for this exact recipe in crypto/finance are thin — nearly all
supporting evidence is backtest research, not disclosed live-trading deployments. Validate rigorously in your
own pipeline (§10) before trusting it over a simpler periodic-retrain-only baseline.
13.2 Multi-asset joint modeling
Running the ensemble's shared feature-extraction layers jointly across BTC plus a small set of correlated major
USDT-margined pairs (e.g. ETHUSDT, SOLUSDT, BNBUSDT) — rather than fully independent per-asset
models — is supported by a converging set of 2025/26 papers on cross-asset attention and cross-sectional
crypto return prediction, and is a productive use of the spare VRAM budget (§11.1). This evidence base is
academic (backtests, not disclosed production systems) — validate the cross-asset variant against the
single-asset baseline using the same kill criteria (§10.3) before trusting it over a simpler independent model.
13.3 Free calibrated uncertainty from spare passes

Multi-level Monte Carlo dropout (a 2026 refinement allocating most stochastic passes to cheap
low-fidelity dropout configurations and only a few to expensive high-fidelity ones) — practical recipe:
~10-30 passes per differentiable member, weighted toward the cheap configurations.

Deep-ensemble spread — already partly free: the 9 heterogeneous members' disagreement is itself an
uncertainty signal, now sharpened by the MC-dropout passes above.

Light test-time augmentation — small input jitter on the recent OHLCV window, forward-passed
alongside the unperturbed input.

Feed the combined distribution's spread into the conformal calibration step (§8.3) so the final confidence
score reflects genuinely more information, not just a relabeled softmax output.

Addendum: Feature Engineering Implementation
 Findings
This addendum documents corrections, gaps, and engineering findings discovered while implementing the
feature-engineering scripts against the real sample data under data/, premium_index/, spot_index/, and
trading/, plus the prior plans/code in Project-IMPJR. The implementation lives in feature engineering
scripts/ as a from-scratch Polars pipeline (config → schemas → utils → parsers → resample →
feature_engine/* → labeling → anti_leakage → publish_to_hf → paths → build_dataset.py). Every item
below was verified empirically against the actual sample files, not assumed from documentation.
1. Corrections to prior assumptions
1.1 Bybit trading/ schema branches by contract type, not by date
The original plan assumed Bybit's tick-trade schema drift (the trailing rpi column) was a function of
calendar date. Verified against samples: the branch is actually by contract type — perpetual symbols
(BTCUSDT, BTCUSD, BTCPERP) always have 11 columns including a trailing rpi field; dated/quarterly
contracts (e.g. BTC-01DEC23, BTCUSDH22, BTCUSDT-01AUG25) always have 10 columns, regardless
of when the file was published. Parsers must branch on column count (or contract-symbol pattern), never
on the file's date. Implemented in parsers/bybit_parser.py:read_bybit_trading().
1.2 Bybit on-disk path convention
Confirmed directory layout (not stated precisely in the original plan):
trading/<symbol>/<symbol><date>.csv.gz,
premium_index/<symbol>/<symbol><date>_premium_index.csv.gz,
spot_index/<symbol>/<symbol><date>_index_price.csv.gz — one file per UTC day per contract
folder, with the premium/spot index filenames carrying an explicit suffix (not just the raw symbol+date).
1.3 Hugging Face publishing layout is flat, not Hive-partitioned
The safest verified pattern in the existing project code (colab_tft_feature_extraction.py /
tft_feature_extraction_2_(2).py) uses a flat data/ prefix with one parquet file per calendar day —
data/features_{symbol}_{date}.parquet — via
huggingface_hub.HfApi().upload_file(repo_type="dataset"), never push_to_hub/upload_folder and never
Hive-style year=/month=/day= partitioning. Reimplemented identically in publish_to_hf.py, with the HF
write token read exclusively from the HF_TOKEN environment variable (several files elsewhere in the
project were found to hardcode a literal token in source — that pattern is not reproduced here or anywhere
in the new scripts).
1.4 The "475 features" figure is a soft target, not a fixed manifest
No file in the prior project enumerates exactly 475 named features; the figure is an emergent count from
the feature-family pool design. The new pipeline does not target an exact count — it implements every
feature family the plan calls for at production quality and deliberately drops placeholder features that had
no real detection logic (several chart-pattern-recognition columns in the old pool were literal always-zero

--- PAGE 32 ---
stubs). The reference build for one sample day (2026-09-06, 10s bars) produces 188 columns including
OHLCV, all engineered features, and labels.
1.5 bookTicker is confirmed stale in both um and cm samples
Only one bookTicker file exists per symbol directory: BTCUSDT (um) is dated 2024-03-30,
BTCUSD_PERP (cm) is dated 2024-10-14. Production code must treat bookTicker as unavailable for any
other day and use bookDepth as the primary source for spread and order-flow imbalance features
(feature_engine/orderbook_microstructure.py falls back to a high-low range proxy spread when
bookTicker is absent).
1.6 fundingRate is monthly-only and lags by about one month
Confirmed: no daily fundingRate path exists anywhere in the vendor layout, only monthly. Critically,
Binance Vision publishes each month's fundingRate dump only after that month ends — the samples'
latest BTCUSDT fundingRate file is 2026-08 while market data (aggTrades etc.) runs into 2026-09, i.e. the
current month's own file is routinely absent for any live/recent day.
parsers/binance_parser.py:read_funding_rate_for_day() walks backward month-by-month (default up
to 6 months) until it finds a published file, so recent days still get the last known funding rate forward-filled
instead of the whole day going null.
1.7 liquidationSnapshot duplicate rows
Confirmed 50% exact-duplicate rows in the cm liquidationSnapshot sample (BTCUSD_PERP, 2024-10-14:
100 raw rows, 50 unique). read_liquidation_snapshot() always deduplicates via .unique(keep="first")
before use.
2. Engineering pitfalls found and fixed during
validation
The following were caught by empirically testing the pipeline against real sample data (a full day of
BTCUSDT um aggTrades, 8640 bars at 10s resolution) rather than by static code review, and are recorded
here since they are exactly the class of subtle correctness bug this plan needs to guard against in any
future implementation of the same feature families:

Polars' dt.dt.hour()/dt.dt.minute() return Int8. Computing hour*60+minute directly overflows Int8's 127
max for any hour ≥ 3 and silently wraps to negative values with no null and no error — it corrupted
every downstream funding-boundary calculation (minutes_to_funding / pre_funding_1h were 53% null
as a symptom). Fix: cast both operands to a wide integer type before combining them.

A single shared safe_div() with a fixed 1e-12 absolute epsilon is appropriate for price-scale ratios but
silently nulls out correlation-style ratios computed from squared returns, whose std-product
denominators sit around 1e-15 by construction (this made vol_clustering_90/360 100% null).
Scale-dependent ratios need a scale-appropriate zero guard (e.g. denom > 0) rather than reusing a
fixed business-scale epsilon everywhere.

An as-of backward join is only correct for sources that represent continuously-updating state (price,
funding rate, open interest, order-book snapshots) where carrying the last known value forward is the

--- PAGE 33 ---
intended semantic. It is the wrong join for discrete sparse events (liquidations): joining a per-bin event
aggregate onto the bar grid with asof-backward causes one liquidation's notional to be carried forward
and re-counted in every subsequent bar and every subsequent rolling window, indefinitely, instead of
only the bin it happened in. The fix is an exact-match join on the (shared, epoch-aligned) bin
timestamp with fill_null(0) for bins with no event.

A feature-family function's early-return branch (used when its source data is absent for the day) must
produce exactly the same column set/dtypes as its populated-data branch, or days with and without
that source will fail to concatenate into a multi-day dataset.
3. Anti-leakage validation performed
anti_leakage.py implements purged + embargoed expanding walk-forward folds (no such implementation
existed anywhere in prior project code) and an empirical leakage self-test that recomputes a feature at
randomly sampled cut points using only truncated data and compares against the full-dataframe value at
the same row. Run against the real built dataset across every leakage-relevant mechanism in the pipeline
— trailing rolling windows (realized_vol_90), manual rolling-covariance ratios (vol_clustering_90), pure
calendar features (minutes_to_funding), as-of-join + forward-fill state features (funding_rate_ma_24h), and
shifted higher-timeframe joins (htf_1m_close) — all passed with zero mismatches.
